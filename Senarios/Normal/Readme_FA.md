# Normal Scenario – Baseline Implementation

در این مرحله، هدف پیاده‌سازی یک نسخه‌ی کامل، پایدار و قابل‌استفاده از سامانه محاسبه قیمت در زمان واقعی بود؛ به‌گونه‌ای که علاوه بر پاسخ‌گویی صحیح به درخواست‌ها، امکان مانیتورینگ، تحلیل عملکرد و انجام تست ظرفیت نیز فراهم باشد.

این سناریو به عنوان **Baseline Architecture** در نظر گرفته شده است؛ یعنی معماری‌ای که ابتدا به‌صورت کامل و عملیاتی پیاده‌سازی شده و سپس در سناریوهای بعدی برای افزایش ظرفیت و کاهش تأخیر بهبود خواهد یافت.

---

## Implemented Components

معماری پیاده‌سازی‌شده شامل اجزای زیر است:

* **FastAPI**

  * دریافت درخواست‌های قیمت
  * تولید `request_id`
  * ارسال درخواست به Kafka
  * انتظار برای نتیجه و بازگرداندن پاسخ به کاربر

* **Kafka**

  * `price_requests` برای درخواست‌ها
  * `price_results` برای نتایج
  * `api_monitoring` برای لاگ‌های مانیتورینگ

* **PySpark Structured Streaming**

  * مصرف پیوسته درخواست‌ها از Kafka
  * بارگذاری اطلاعات مرجع از ClickHouse
  * محاسبه:

    * قیمت محصولات
    * هزینه حمل
    * مالیات
    * تخفیف
  * تولید نتیجه و ارسال به Kafka

* **ClickHouse**

  * ذخیره جداول مرجع:

    * `tax_rates`
    * `shipping_fees`
    * `promotions`
  * ذخیره لاگ‌های مانیتورینگ:

    * `api_performance_logs`

* **Grafana + Prometheus**

  * مانیتورینگ منابع سیستم
  * مانیتورینگ API
  * مشاهده RPS، زمان پاسخ و وضعیت درخواست‌ها

* **Locust**

  * تولید بار تست
  * اجرای تست‌های مرحله‌ای و پیوسته

## Monitoring

برای تحلیل عملکرد سیستم، اطلاعات زیر در ClickHouse ذخیره شد:

* زمان پاسخ
* وضعیت درخواست (`SUCCESS`, `TIMEOUT`)
* اندازه درخواست
* قیمت نهایی
* شناسه درخواست و کاربر

این داده‌ها امکان تحلیل دقیق رفتار سیستم در شرایط مختلف بار را فراهم می‌کنند.

نمونه داشبورد مانیتورینگ:

* `Monitoring_Log_Result.png`

## Load Test Scenarios

دو روش تست اجرا شد:

### 1. Interval Load Test

در این روش، بار سیستم به‌صورت مرحله‌ای افزایش یافت:

100 → 200 → 300 → ... → 1000 Users

هر مرحله حدود ۵ دقیقه اجرا شد.

نتایج:

* سیستم در این شرایط پایدار بود.
* خطای قابل‌توجهی مشاهده نشد.
* معماری توانست بارهای متوسط را بدون مشکل مدیریت کند.

تصویر نتایج:

* `Locust_Result_Server2_Interval.png`

---

### 2. Continuous Load Test

در این سناریو:

* Users = 2000
* Ramp Up = 5 Users/sec

بار به‌صورت پیوسته افزایش یافت.

نتایج:

* ابتدا RPS افزایش پیدا کرد.
* پس از رسیدن سیستم به ظرفیت پردازشی، افزایش کاربران دیگر باعث افزایش Throughput نشد.
* زمان پاسخ به‌تدریج افزایش یافت.
* بخشی از درخواست‌ها به دلیل عبور از Timeout شکست خوردند.

تصویر نتایج:

* `Locust_Result_Server2_Continues.png`

* در نهایت زمان پردازش از Timeout API عبور کرده و درخواست‌ها Fail می‌شوند.
